# FileScope V5.1.0 performance record

Measured 2026-10-13 on the same Windows host (Intel i7-11700K, 8C/16T, 17 GB),
Python 3.11.9, the same generated corpora and the same settings, comparing the
RC2 source tree (`2801304`) with the V5.1.0 working tree. Median of the stated
number of runs unless a sample list is shown. Raw JSON is in
`raw/v5.1.0/`. The harness that produced it is committed as
`scripts/perf_stage.py` (pipeline stages), `scripts/perf_scaling.py` (worker
scaling) and `scripts/perf_gui.py` (UI-thread cost and first-result latency).
Files prefixed `before-` come from the RC2 worktree at `2801304`; the older
`head-` files are the same tree measured in place and agree with them within
run-to-run noise.

The corpora are generated text files (2,000 and 10,000 files, ~1.2 kB each, 41
lines per file). They are **not** representative of Office/PDF payloads, SMB
latency, OCR or cloud-only files; those paths are covered by tests, not by
these timings.

## 1. What the investigation found

Splitting a search into its stages (enumeration, index lookup, extraction,
matching, result production) showed that the pipeline itself was not slow, but
that **the indexed path lost badly as soon as more than one worker touched it**.
On the 2,000-file corpus with a warm index, the same work took:

| Worker threads | RC2 wall | RC2 CPU | V5.1.0 wall | V5.1.0 CPU |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 0.54 s | 0.70 s | 0.54 s | 0.61 s |
| 2 | 0.87 s | 1.16 s | — | — |
| 4 (default) | 1.68 s | 2.86 s | 0.66 s | 0.78 s |
| 8 | 2.05 s | 3.78 s | — | — |

and on the 10,000-file corpus:

| Worker threads | RC2 wall | RC2 CPU | V5.1.0 wall | V5.1.0 CPU |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 2.96 s | 3.66 s | 2.81 s | 3.55 s |
| 2 | — | — | 3.47 s | 4.09 s |
| 4 (default) | 9.50 s | 15.86 s | 3.60 s | 4.32 s |
| 8 | — | — | 3.59 s | 4.26 s |

Serving files from the index is pure Python plus sqlite3 row fetching, so the
GIL serialises it anyway — and letting four threads interleave it made every one
of them several times more expensive (CPU time grew 5x while wall time grew
3x). The fix serialises the index lookups and verdicts with one lock; file
extraction still uses the whole worker pool. Single-threaded time is unchanged
(2.96 s → 2.81 s on 10,000 files, inside run-to-run variance), so nothing was
traded away to get the multi-worker numbers.

## 2. End-to-end scenarios (2,000 files, median of 3)

| Scenario | RC2 | V5.1.0 | Change |
| --- | ---: | ---: | ---: |
| Direct full search (index off) | 0.678 s | 0.651 s | -4% |
| Standard mode, warm index | 2.095 s | 0.671 s | **-68%** |
| Standard mode, selective query (`評価 & BBB`) | 0.704 s | 0.364 s | -48% |
| Search 1 + Search 2 (combined query, warm index) | 2.513 s | 0.847 s | **-66%** |
| Fast mode (index only) | 1.823 s | 0.672 s | -63% |
| First result, warm index (pipeline only) | 0.048 s | 0.032 s | — |
| Cancel after 50 ms, index off | 1 ms | 1 ms | — |
| Cancel after 50 ms, warm index | 3.1 ms | 2.3 ms | — |
| Index build, 2,000 files (cold) | 8.35 s | 8.3–8.5 s | unchanged |
| Index build, 10,000 files (cold) | 46.1 s | 46.3 s | unchanged |

Cold index building is extraction-bound and unchanged; the fix targets the
"already indexed, search again" case, which is the common repeat search.

## 3. GUI-side measurements

The window was driven through a real (hidden) Tk root with the actual
`MainWindow`, recording the time the UI thread spends in its own callbacks and
the worst gap between 40 ms timer callbacks.

| Scenario (2,000 files) | RC2 | V5.1.0 |
| --- | ---: | ---: |
| First result visible after pressing 検索開始 | 0.203–0.226 s | 0.105–0.135 s |
| List rebuilds during a cold-build search | 45 | 23 |
| Total list-rebuild time in that search | 0.735 s | 0.361 s |
| Worst UI-thread stall during warm-index search | 0.072 s | 0.067 s |
| Selection kept after a list rebuild mid-search | 5 of 238 ticks | 231 of 231 ticks |
| Preview cleared by the app's own redraw | yes | no |

The 200 ms delay before the first result was the UI drain cadence, not the
pipeline: the pipeline had the first hit at 32 ms. The UI now drains
immediately when a search starts and every 100 ms while one is running, and
rebuilds the list at most every 400 ms (progress counters still update on every
drain). A rebuild costs ~15–30 ms per 1,000s of visible rows, so capping it
keeps the progress display live without making the window heavy.

10,000 results, warm index, end to end through the GUI: 3.46 s wall, 9 list
rebuilds, 0.30 s of UI-thread redraw time (8.7% duty). Before the changes, the
same 10,000-result search rebuilt the list 244 times in 56 s and spent 7.27 s
in the UI thread — but that run also included the cold index build, so the two
figures are not directly comparable; the duty cycle (4.4 → 2.6 rebuilds/s) is.

## 4. Memory and package size

Peak working set for a 2,000-file search stayed at ~92 MB before and after; the
10,000-file search peaked at ~84 MB in both.

The expanded portable bundle is 67,281,103 bytes against RC2's 67,135,812
(+145 KB, +0.2%), and the whole difference is documentation: a file-by-file
comparison of the two bundles shows no file that RC2 shipped is missing, and the
only additions are the v5.1.0 performance record, the release notes and the raw
runs. No dependency was added. Zip size depends on how well the frozen
executable and the `.pyd`/`.dll` set compress on a given build, so the published
zip is quoted in the release notes rather than compared here.

## 5. Startup of the shipped bundle

The app logs its own startup milestones, so each build was launched with a
redirected `LOCALAPPDATA` and the log was read back. `first_ui_idle` is measured
from the start of `run_gui()` to Tk's first idle callback; it therefore covers
the UI import, the stale-temporary-file sweep, the OCR probe, window
construction and the first list fill, but not process creation.

| Build | first_ui_idle, three runs | median |
| --- | --- | ---: |
| frozen v5.1.0 (`dist/FileScope`) | 0.275 s / 0.345 s / 0.482 s | 0.345 s |
| frozen 5.1.0-rc2 (`dist/rc2/FileScope`) | 0.306 s / 0.363 s / 0.690 s | 0.363 s |
| source v5.1.0 | 0.414 s / 0.469 s / 0.533 s | 0.469 s |

The window reaches its first idle as quickly as RC2 (the difference is inside
run-to-run spread) and the frozen build is not slower than the source tree.
The RC1/RC2 figure quoted earlier in this project (208.3 ms → 226.2 ms per
startup) used a different definition — the in-process construction of the
window — so it is not comparable with these numbers; what matters here is that
v5.1.0 did not move in either direction.

The frozen bundle also searched a 2,000-file corpus the same way the source
tree did: 286 hits, 2,000 files scanned, 0 errors, the same file set. The first
run of the freshly built executable took 7.8 s against 1.0 s for the source
build, but that was a cold read of a file the antivirus had just scanned; three
warm repeats took 0.72–0.77 s (frozen) against 0.95–1.06 s (source).

## 6. Not measured on this host

- Real Office/PDF corpora, SMB shares, OneDrive/SharePoint online-only files and
  actual Tesseract OCR: no such environment exists here.
- Frozen-EXE startup and the portable bundle's first-window time beyond the
  `--self-test` / `--diagnostics` runs recorded in the validation notes.
- Behaviour under an externally loaded machine: all numbers above come from
  repeated runs on an otherwise idle host, and differences below ~10% are
  treated as noise rather than as gains.
