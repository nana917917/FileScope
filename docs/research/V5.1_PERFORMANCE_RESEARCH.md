# 検索中の体感・進捗・プレビューに関する追加調査（V5.1.0）

既存の製品比較（8製品・16情報源）は `docs/research/UX_BENCHMARK.md` にあります。
ここでは rc2 以降の「検索中が重い」という実機の感想に対して、**何を計測し、
どの設計判断につなげたか**だけを追記します。製品の一般的な説明をそのまま
FileScope の根拠にはしていません。

## 1. 今回の論点

| 論点 | 調査で確かめたいこと | 結論（本リポジトリでの対応） |
| --- | --- | --- |
| 検索中の応答性 | 検索が遅いのか、GUI更新が重いのか | 計測で分離。索引検索のスレッド競合が主因（`docs/performance/V5.1.0.md`） |
| 結果の段階表示 | 逐次表示と一覧更新の頻度 | 進捗は100 ms、一覧再構築は400 msに分離 |
| 索引と直接検索 | どちらを優先するか | 「索引は候補を絞るだけ、合否は本文と同じ判定」を維持 |
| 進捗の粒度 | 総数不明時の見せ方 | 総数確定まで不定バー（偽の%を出さない）を維持 |
| プレビューの分離 | 検索を妨げないか | 選択した1件だけを別スレッドで読む方式を維持 |

## 2. 参考にした一般に知られている設計（公式情報 / 実利用の報告 / 推測の区別）

以下は **FileScope の実装判断の背景**として参照した一般的な説明です。個々の
ベンダー資料を今回新たに引用・検証したものではないため、断定はしません。

- **名前・属性だけの高速列挙**（Everything / WizFile 系）
  — NTFS の USN ジャーナルや MFT を使い、内容を読まずに一覧を出す設計が
  公式に説明されています。FileScope は同種の特権APIを使わず、`scandir` で
  属性だけを読む列挙を維持しています（内容を読まない点だけを踏襲）。
- **内容検索の索引と、索引に無いものの直接読み**
  — Agent Ransack / FileLocator、DocFetcher、AnyTXT Searcher などは
  「索引済みは速い／未索引は読む」という二段構えで、索引が答えられない語
  （日本語1〜2文字など）は走査に落ちる点が共通して説明されています。
  FileScope の「索引は候補絞り込み、判定は共通ロジック」はこの整理と同じです。
- **進捗の見せ方**
  — 総数が確定する前に割合を出す製品は少なく、件数や現在の対象を出すか
  不定バーにするのが一般的です。実利用の報告でも「%が当てにならない」という
  不満が繰り返し現れます。FileScope が総数確定まで%を出さないのはこのためです。
- **応答性の確保**
  — 実利用の報告では「UIが固まる」「スクロールが飛ぶ」が最も嫌われる一方、
  逐次表示そのものは歓迎されています（推測ではなく、レビューで繰り返し出る
  指摘の傾向）。今回の修正はこの2点（UIを止めない・選択と表示位置を壊さない）
  に対応しています。
- **プレビューの分離**
  — 一覧表示のために全ファイルのプレビューを作る製品はなく、選択時にだけ
  本文を読む方式が一般的です。FileScope も同方式を維持し、検索中の描画は
  選択した1件に限定しています。

## 3. 実装に結びついた判断

1. **索引参照の直列化**（`filescope/core/coordinator.py`）
   — 索引判定はGILで並列化できないため、ワーカーを増やすほど遅くなることを
   実測。直列化が唯一の正解でした（推測ではなく計測に基づく）。
2. **進捗と一覧更新の分離**（`filescope/ui/main_window.py`）
   — 「進捗はこまめに、重い一覧再構築は控えめに」。
3. **総数不明時に%を出さない**方針は変更なし（偽の進捗を出さない）。
4. **プレビューは選択時のみ**、検索スレッドとは別スレッドで実行（変更なし）。
5. **索引ON/OFFで結果が変わらない**ことを引き続きテストで固定。

## 4. 調査で採らなかった案

- 索引を別スレッド群に分けて並列読み出し（実測で悪化。採用せず）
- 検索対象の事前全件列挙による正確な%（起動と初回表示が遅くなるため不採用）
- 一覧の逐次表示を止めて完了時に一括表示（体感が悪化するため不採用）
- 一覧の並びを検索中だけ到着順にする案（並びの意味が変わるため保留）
